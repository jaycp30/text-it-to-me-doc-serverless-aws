# Goal

Build RxReader — a serverless web app that reads handwritten doctor prescriptions via AI vision, generates a medication schedule, sends dose reminders via SMS/email, and lets users chat with an AI assistant about their medications.

---

## Current State

Backend Lambda functions are fully written and ready to deploy — not yet deployed. Frontend React component is complete with working UI (prescription upload, schedule view with taper visualization, chatbot drawer). Everything has been built and designed in this Claude.ai session but no code has been pushed to GitHub or deployed to AWS yet.

The frontend artifact preview works end-to-end: uploads a prescription image, calls the Anthropic API directly from the browser, parses the JSON response, and renders the schedule. The chat feature works the same way in the artifact. In the real deployed app, both of these calls go through backend Lambdas that call Bedrock instead.

## Changed This Session

Everything was built from scratch in this session. Key decisions made:

**Architecture:**
- SAM for backend (Lambda + API Gateway + DynamoDB + S3 + EventBridge + SNS/SES)
- Amplify for frontend (hosting + Cognito auth + CI/CD from GitHub)
- No AWS Chatbot service — chatbot is just a new Lambda calling Bedrock
- No Textract — Claude vision handles OCR + interpretation in one step (critical for handwritten prescriptions with ditto marks, tapers, shorthand)
- Tokyo region (ap-northeast-1) throughout

**Notification strategy (both Option A + B):**
- Option A: Per-dose EventBridge Scheduler rules, one per dose event, auto-delete after firing
- Option B: Hourly cron Lambda checks if it's 8am in each user's timezone, sends daily summary
- SMS via SNS direct publish (transactional, not promotional — fewer Philippines carrier restrictions)
- Email via SES as fallback/alternative
- User picks SMS or email at onboarding, stored in DynamoDB with their timezone

**Frontend design decisions:**
- Warm parchment canvas (#F8F6F1) — deliberately not clinical white + teal (healthcare reflex rejected)
- Soft sage green (#5E7E68) accent — calming, natural
- Newsreader serif headings + DM Sans body + DM Mono for times/doses
- Three tabs on schedule screen: Today (timeline), Upcoming (7 days, collapsible), Medications (cards with taper viz)
- Taper visualization: horizontal bar chart showing decreasing Prednisone doses day by day, today highlighted
- Disclaimer added in two places: home screen (before upload) and schedule screen Today/Upcoming tabs (at point of action)
- Floating chat button (bottom right) opens drawer from bottom
- Chat: 5 pre-seeded questions from actual prescription, last 6 messages kept for context window management

**Chat guardrails in system prompt:**
- Only discuss medications in the current prescription
- Never recommend dose changes or stopping medication
- Never diagnose
- Emergency symptoms → tell user to stop and go to ER immediately
- Off-topic questions → politely decline
- Session-only (not persisted), noted to user in chat drawer
- max_tokens: 512 per chat response to keep costs low (~$0.01-0.02 per message)

**Prescription processing:**
- Frontend gets presigned S3 URL → uploads image directly to S3 → calls /process with imageKey
- Lambda fetches image from S3, sends to Bedrock Claude (multimodal), parses JSON response
- Saves to DynamoDB (prescriptions table + schedules table)
- Creates EventBridge Scheduler rules for each future dated dose
- Skips PRN (as needed) meds and past-dated doses for scheduling

## Failed Attempts

None this session — this was greenfield design and build, no debugging cycles. However, note these known gotchas for when you start deploying:

**Bedrock model access** — easy to forget, will cause silent failures. Go to AWS Console → Bedrock → Model Access → request Claude access before first deploy. Can take a few minutes to activate.

**SES sandbox** — new AWS accounts are in SES sandbox mode, can only send to verified emails. Request production access before testing with real users. Or verify your own email first for dev testing.

**EventBridge Scheduler ActionAfterCompletion: DELETE** — this is set so rules auto-clean after firing. If you remove it, you'll accumulate thousands of stale rules.

**Philippines SMS (+63)** — SNS direct publish works but delivery is carrier-dependent. Test with your own number first. Set SMSType to "Transactional" (already done in notifyUser Lambda) for better delivery priority.

**Bedrock model ID in Tokyo** — the template.yaml default is `us.anthropic.claude-3-5-sonnet-20241022-v2:0`. Verify this in the Bedrock console under Base Models in ap-northeast-1 before deploying. Cross-region inference profiles use the `us.` prefix.

## Architecture Reference

```
Amplify (React frontend + Cognito auth)
    |
    ▼
API Gateway HTTP API (ap-northeast-1)
    |
    ├── POST /upload-url      → getUploadUrl Lambda    → S3 presigned PUT URL
    ├── POST /process         → processPrescription Lambda
    │                               → S3 (fetch image)
    │                               → Bedrock Claude vision (no OCR — direct image)
    │                               → DynamoDB (prescriptions + schedules tables)
    │                               → EventBridge Scheduler (1 rule per future dose)
    ├── POST /chat            → chatLambda (NOT YET WRITTEN — next task after deploy)
    │                               → Bedrock Claude Sonnet
    │                               → prescription JSON as system prompt context
    └── GET  /schedules       → getSchedules Lambda     → DynamoDB read

EventBridge Scheduler (per dose, auto-deletes after firing)
    → notifyUser Lambda → SNS (SMS) or SES (email)

EventBridge cron (every hour)
    → dailySummary Lambda → checks if 8am in user timezone → notifyUser Lambda
```

## Key Tech Decisions Summary

| Decision | Choice | Why |
|---|---|---|
| OCR | None — Claude vision direct | Handles ditto marks, tapers, shorthand in one step |
| Backend IaC | SAM | Already familiar from hiking app |
| Frontend hosting | Amplify | Zero-config Cognito + CI/CD |
| Scheduling | EventBridge Scheduler (Option A) + hourly cron (Option B) | Per-dose precision + daily summary |
| SMS | SNS direct publish | No topic needed, transactional priority |
| Email | SES | Fallback to SMS, verified sender |
| Chat persistence | Session only (for now) | Simpler, DynamoDB storage can be added later |
| Chat context window | Last 6 messages | 3 turns, prevents token creep |
| Region | ap-northeast-1 (Tokyo) | Consistent with hiking app |
